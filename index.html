01_onde_paramos.md

Onde Paramos — e Para Onde Vamos

Na aula passada, vocês construíram uma Biblioteca inteira com SQLiteOpenHelper: escreveram o CREATE TABLE à mão, montaram ContentValues pra inserir e percorreram Cursor pra ler. Funcionou — mas exigiu bastante código repetitivo.

Hoje, duas coisas mudam ao mesmo tempo: o banco escrito à mão vira Room (a biblioteca que automatiza o que vocês fizeram manualmente), e a Biblioteca deixa de depender só do que o usuário digita — ela passa a buscar livros de verdade numa API e guardar o resultado localmente.

Nada do trabalho passado se perde: o modelo Livro continua o mesmo. A arquitetura em camadas (model / database / repository / viewmodel / ui) continua a mesma. Só o conteúdo do pacote database e do Repository muda.
02_room_migracao.kt

Migrando de SQLite Manual para Room

Room não é um banco diferente — é uma camada de abstração sobre o mesmo SQLite que vocês já usaram. A diferença é que, em vez de escrever SQL e mapear Cursor à mão, vocês descrevem a estrutura com anotações e o Room gera o resto em tempo de compilação.

Aula passada (manual)Hoje (Room)
execSQL("CREATE TABLE ...")@Entity numa data class
ContentValues + db.insert()@Insert numa interface @Dao
Cursor + moveToNext() manualFlow<List<Entity>> automático
SQLiteOpenHelperRoomDatabase (mesmo padrão singleton)
Room não substitui o entendimento de SQLite — ele automatiza. Quem escreveu a versão manual na aula passada agora entende exatamente o que essas anotações estão gerando por baixo dos panos.

O que é um ORM, e por que ele existe

O Room pertence a uma categoria de ferramentas chamada ORM (Object-Relational Mapping, ou mapeamento objeto-relacional). O nome descreve exatamente o problema que ela resolve: existe uma incompatibilidade natural entre dois mundos.

  • No código, pensamos em objetos: um Livro com propriedades, que pode conter outros objetos dentro.
  • No banco relacional, tudo é tabela: linhas e colunas de tipos simples, sem hierarquia.

Alguém precisa traduzir entre os dois formatos. Na aula passada, esse alguém era você — escrevendo ContentValues na ida e percorrendo o Cursor na volta. Um ORM automatiza essa tradução: você descreve o formato uma vez, com anotações, e a biblioteca gera o código de conversão.

ORMs não são exclusivos do Android nem do Kotlin. É um conceito presente em praticamente toda plataforma que fala com banco relacional. Reconhecer o padrão vale muito mais do que decorar as anotações do Room especificamente.

O que o Room ganha (e o que ele cobra)

VantagemO que isso significa na prática
Erros de SQL em tempo de compilação Se você digitar errado o nome de uma coluna dentro de uma @Query, o projeto não compila. Na versão manual, esse mesmo erro só apareceria com o app rodando, na forma de um crash.
Muito menos código repetitivo As ~30 linhas de Cursor e mapeamento manual da aula passada viram uma linha de anotação.
Atualização automática da tela Com Flow, gravar no banco atualiza a interface sozinho. Sem isso, era preciso lembrar de reconsultar manualmente após cada escrita — e esquecer disso era um bug silencioso.
Segurança de thread O Room se recusa a rodar consultas na Main Thread por padrão, evitando o travamento que na versão manual dependia da nossa disciplina.

Em troca, o Room cobra: uma dependência extra, um plugin de compilação (KSP) e um tempo de build um pouco maior. Para um app com uma tabela só, é discutível. Para um app real, com várias entidades e relações, o custo se paga rápido.

Onde isso está no mercado: o Room faz parte do conjunto Jetpack, mantido pelo próprio Google, e é a solução de persistência local recomendada oficialmente para apps Android. Na prática, é o que você vai encontrar na maior parte dos projetos profissionais — e o que costuma ser cobrado em processos seletivos quando o assunto é banco de dados no Android.
03_api_livros.kt

Consumindo uma API de Livros de Verdade

Vamos usar a Open Library API — gratuita, pública e sem necessidade de chave de acesso. Um único endpoint de busca:

GET 
https://openlibrary.org/search.json?q=harry+potter&limit=20

A resposta traz uma lista docs, cada item com título, lista de autores e ano de primeira publicação — exatamente os três campos que já existem no modelo Livro.

Reaproveitando a aula de APIs: Retrofit + Coroutines continuam do jeito que já foi ensinado — suspend fun, Dispatchers.IO, conversão de JSON com GSON. Nada disso é novo; é a mesma disciplina aplicada a um endpoint diferente.
04_repository_ssot.kt

O Repository como Fonte Única de Verdade

Com Room e API convivendo no mesmo Repository, surge uma pergunta de arquitetura: quem a tela deveria escutar — a API ou o banco? A resposta do padrão Single Source of Truth (SSoT) é: só o banco. A API existe apenas para alimentar o Room.

Cenário sem SSoT, pra entender o problema que ele resolve: imagine que a tela lesse a API diretamente e o Room fosse só um "plano B" separado. Toda tela precisaria de uma lógica do tipo "tento a API; se der erro, busco no Room; se os dois derem resultados diferentes, qual eu mostro?" — repetida em cada lugar que precisar dos dados. Com SSoT, essa pergunta desaparece: existe um único lugar de leitura (o Room), então nunca há dois resultados conflitantes pra decidir entre.

A tela nunca lê da API diretamente. Ela observa o Room; a API só escreve nele quando o usuário busca algo novo.

Duas responsabilidades, duas funções

  • Observar — observeLivros(): Flow<List<Livro>>, sempre lendo do Room.
  • Buscar e Armazenar — suspend fun buscarEArmazenar(query: String), que consulta a API e grava o resultado no Room. Não devolve nada direto pra tela.
Consequência prática: se a busca falhar (sem internet, por exemplo), os livros já salvos continuam na tela normalmente — só a tentativa de buscar mais falha, isolada num estado separado de erro.

O que torna o Flow "automático"

Um Flow vindo de uma @Query do Room não é uma lista fixa — é uma assinatura. O Room instrumenta a tabela para avisar todo mundo que está observando sempre que uma linha muda. Concretamente: quando buscarEArmazenar() chama dao.insertAll(...), o Room detecta a escrita na tabela livros e empurra uma nova lista pra qualquer Flow que esteja observando aquela tabela — sem que ninguém precise chamar um "atualizar tela" manualmente. É por isso que a UI não tem nenhum código do tipo onSearchComplete { refreshList() }: a atualização acontece como efeito colateral automático de gravar no banco.

C. Plugins (build.gradle.kts - Module :app)

Aplique o alias do plugin KSP no topo do arquivo do módulo da aplicação:

build.gradle.kts (Module :app) 
plugins {
    alias(libs.plugins.android.application)
    alias(libs.plugins.kotlin.android)
    alias(libs.plugins.kotlin.compose)
    alias(libs.plugins.ksp)
}
O que o KSP faz de verdade: as anotações @Entity, @Dao e @Database sozinhas não fazem nada em tempo de execução — são só "marcações". O KSP (Kotlin Symbol Processing) lê essas marcações durante a compilação e gera, automaticamente, as classes Kotlin de verdade que implementam o SQL por trás delas (o equivalente ao DatabaseHelper que vocês escreveram à mão na aula passada). Por isso o app não compila sem o plugin: sem ele, as anotações ficam sem nenhuma implementação gerada por trás.

D. Dependências (build.gradle.kts - Module :app)

Adicione as referências das bibliotecas apontando para o Version Catalog:

build.gradle.kts (Module :app) 
dependencies {

    // Room: persistência local, agora automatizada
    implementation(libs.room.runtime)
    implementation(libs.room.ktx)
    ksp(libs.room.compiler)
}

package com.seunome.biblioteca.database

import android.content.Context
import androidx.room.Database
import androidx.room.Room
import androidx.room.RoomDatabase

@Database(entities = [LivroEntity::class], version = 1, exportSchema = false)
abstract class BibliotecaDatabase : RoomDatabase() {

    abstract fun livroDao(): LivroDao

    companion object {
        @Volatile private var INSTANCE: BibliotecaDatabase? = null

        fun getInstance(context: Context): BibliotecaDatabase {
            return INSTANCE ?: synchronized(this) {
                Room.databaseBuilder(
                    context.applicationContext,
                    BibliotecaDatabase::class.java,
                    "biblioteca.db"
                )
                    .fallbackToDestructiveMigration()
                    .build()
                    .also { INSTANCE = it }
            }
        }
    }
}

import com.google.gson.annotations.SerializedName
import retrofit2.Retrofit
import retrofit2.converter.gson.GsonConverterFactory
import retrofit2.http.GET
import retrofit2.http.Query

data class OpenLibraryResponse(
    val docs: List<BookDoc>
)

data class BookDoc(
    val title: String,
    @SerializedName("author_name") val authorName: List<String>?,
    @SerializedName("first_publish_year") val firstPublishYear: Int?
)

interface OpenLibraryService {
    @GET("search.json")
    suspend fun buscarLivros(
        @Query("q") query: String,
        @Query("limit") limit: Int = 20
    ): OpenLibraryResponse
}

object RetrofitClient {
    private const val BASE_URL = "https://openlibrary.org/"

    val api: OpenLibraryService by lazy {
        Retrofit.Builder()
            .baseUrl(BASE_URL)
            .addConverterFactory(GsonConverterFactory.create())
            .build()
            .create(OpenLibraryService::class.java)
    }
}

Passo 4 — Repository: Observar e Buscar 4 de 7

Local: pacote repository  |  Arquivo: LivroRepository.kt

repository/LivroRepository.kt 
package com.seunome.biblioteca.repository

import com.seunome.biblioteca.database.LivroDao
import com.seunome.biblioteca.database.LivroEntity
import com.seunome.biblioteca.model.Livro
import com.seunome.biblioteca.network.BookDoc
import com.seunome.biblioteca.network.OpenLibraryService
import com.seunome.biblioteca.network.RetrofitClient
import kotlinx.coroutines.flow.Flow
import kotlinx.coroutines.flow.map

class LivroRepository(
    private val dao: LivroDao,
    private val api: OpenLibraryService = RetrofitClient.api
) {
    // Observar: a tela se inscreve aqui uma única vez
    fun observeLivros(): Flow<List<Livro>> =
        dao.observeAll().map { entidades -> entidades.map { it.toDomain() } }

    // Buscar e Armazenar: só alimenta o Room, não devolve nada direto pra tela
    suspend fun buscarEArmazenar(query: String) {
        val resposta = api.buscarLivros(query)
        dao.insertAll(resposta.docs.map { it.toEntity() })
    }
}

private fun LivroEntity.toDomain() = Livro(id = id, titulo = titulo, autor = autor, ano = ano)

private fun BookDoc.toEntity() = LivroEntity(
    titulo = title,
    autor = authorName?.firstOrNull() ?: "Autor desconhecido",
    ano = firstPublishYear ?: 0
)

Passo 5 — ViewModel: AndroidViewModel + Dois Estados 5 de 7

Local: pacote viewmodel  |  Arquivo: BibliotecaViewModel.kt

viewmodel/BibliotecaViewModel.kt 
package com.seunome.biblioteca.viewmodel

import android.app.Application
import androidx.compose.runtime.getValue
import androidx.compose.runtime.mutableStateOf
import androidx.compose.runtime.setValue
import androidx.lifecycle.AndroidViewModel
import androidx.lifecycle.viewModelScope
import com.seunome.biblioteca.database.BibliotecaDatabase
import com.seunome.biblioteca.model.Livro
import com.seunome.biblioteca.repository.LivroRepository
import kotlinx.coroutines.flow.SharingStarted
import kotlinx.coroutines.flow.StateFlow
import kotlinx.coroutines.flow.stateIn
import kotlinx.coroutines.launch

sealed interface BuscaState {
    object Idle : BuscaState
    object Loading : BuscaState
    data class Error(val message: String) : BuscaState
}

class BibliotecaViewModel(application: Application) : AndroidViewModel(application) {

    private val repository = LivroRepository(
        dao = BibliotecaDatabase.getInstance(application).livroDao()
    )

    // Fonte única: sempre reflete o que está salvo no Room
    val livros: StateFlow<List<Livro>> = repository.observeLivros()
        .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5000), emptyList())

    var buscaState: BuscaState by mutableStateOf(BuscaState.Idle)
        private set

    fun buscar(query: String) {
        if (query.isBlank()) return
        viewModelScope.launch {
            buscaState = BuscaState.Loading
            buscaState = try {
                repository.buscarEArmazenar(query)
                BuscaState.Idle
            } catch (e: Exception) {
                BuscaState.Error("Não foi possível buscar agora. Mostrando livros salvos.")
            }
        }
    }
}
Decifrando .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5000), emptyList()):
  • repository.observeLivros() devolve um Flow "frio" — ele só começa a observar o Room quando alguém de fato se inscreve nele.
  • stateIn transforma esse Flow num StateFlow: sempre guarda o último valor, para que a tela tenha algo pra mostrar imediatamente, mesmo antes de uma nova emissão.
  • SharingStarted.WhileSubscribed(5000) diz: "continue observando o Room enquanto a tela estiver visível, e por mais 5 segundos depois que ela sair de tela" — esse pequeno atraso evita reiniciar a observação do zero em rotações rápidas de tela ou trocas de abas.
  • emptyList() é o valor inicial, usado só no instante entre o app abrir e o Room responder pela primeira vez.

O ponto alto da aula: a lista (LazyColumn) nunca depende diretamente da busca. Ela só observa o Room. A busca só existe para alimentar o Room — exatamente o diagrama de Single Source of Truth, agora rodando de verdade.

Sua Biblioteca está sincronizada se…

  • Buscar por um título real (ex: "harry potter") preenche a lista com resultados da Open Library.
  • Fechar e reabrir o app mantém os livros buscados anteriormente, mesmo offline.
  • Desligar a internet e tentar buscar mostra um aviso — sem apagar os livros já salvos.
  • O Database Inspector mostra a tabela livros populada com dados vindos da API.
  • Nenhuma classe de ui ou viewmodel importa Retrofit ou Room diretamente — só o Repository.
07_troubleshooting.md

Erros Comuns e Como Resolver

O Room adiciona um passo de geração de código na compilação, o que cria uma família de erros nova. Procure aqui antes de recomeçar o projeto.

Cannot find implementation for BibliotecaDatabase. BibliotecaDatabase_Impl does not exist

Causa: o KSP não rodou. As anotações @Entity, @Dao e @Database sozinhas não fazem nada — quem gera a implementação de verdade é o processador, durante a compilação.

Solução: confirme que o plugin id("com.google.devtools.ksp") está no bloco plugins { } e que a linha ksp("androidx.room:room-compiler:2.6.1") está em dependencies { }. Depois faça Build > Clean Project e sincronize.

Atenção: tem que ser ksp(...), não implementation(...), nessa linha específica do compilador.

Room cannot verify the data integrity / Migration didn't properly handle

Causa: você alterou a estrutura de uma @Entity (adicionou um campo, mudou um tipo) sem aumentar o número da version no @Database. O banco no aparelho tem uma estrutura diferente da que o código espera.

Solução em desenvolvimento: desinstale o app do emulador e rode de novo. Como usamos fallbackToDestructiveMigration(), aumentar a version também resolve — o Room apaga e recria o banco.

Em produção seria diferente: apagar o banco significaria perder os dados do usuário. Aí é necessário escrever uma migração de verdade, que transforma a estrutura antiga na nova preservando o conteúdo.

Not sure how to convert a Cursor to this method's return type

Causa: o tipo de retorno declarado no @Dao não corresponde ao que a consulta devolve — por exemplo, uma @Query que seleciona todas as colunas de livros, mas cujo retorno declarado não é LivroEntity.

Solução: confirme que o tipo dentro de Flow<List<...>> é exatamente a classe anotada com @Entity daquela tabela.

Cannot access database on the main thread

Causa: uma operação de banco foi chamada fora de uma Coroutine. O Room bloqueia isso de propósito, para não deixar a interface travar.

Solução: funções de escrita no @Dao devem ser suspend, e devem ser chamadas dentro de viewModelScope.launch { }. Já as funções de leitura que retornam Flow não precisam ser suspend — o Flow já é assíncrono por natureza.

A lista não atualiza depois de buscar na API

Verifique nesta ordem:

1. A tela está usando collectAsState() no StateFlow? Sem isso, o Compose não observa as mudanças.

2. O buscarEArmazenar() realmente chama dao.insertAll(...)? É a gravação no banco que dispara a atualização — não a resposta da API.

3. A @Query de leitura e o @Insert estão na mesma tabela? O Room só notifica quem observa a tabela que foi alterada.

requires libraries and applications that depend on it to compile against version 36 (ou 37) or later

Causa: alguma biblioteca ficou mais nova que o compileSdk do projeto. Costuma acontecer quando o "AGP Upgrade Assistant" é aceito e reescreve o libs.versions.toml.

Solução: volte o bloco [versions] para os valores fixados na aula passada e confirme compileSdk = 35. Procure também entradas duplicadas no arquivo (ex: um coreKtxVersion além do coreKtx) — apague as duplicadas e qualquer linha do build.gradle.kts que as referencie.

Unable to resolve host / falha ao buscar na Open Library

Causa mais comum: falta a permissão de internet. O projeto da aula passada não precisava dela, porque não acessava a rede.

Solução: confirme que <uses-permission android:name="android.permission.INTERNET" /> está no AndroidManifest.xml, acima da tag <application>.

Comportamento esperado: mesmo sem internet, os livros já salvos devem continuar aparecendo. Se a tela ficar vazia, o problema não é a rede — é o Single Source of Truth não estar implementado corretamente.

Quero confirmar que os dados foram mesmo gravados

Com o app rodando, abra View > Tool Windows > App Inspection > Database Inspector. Você verá a tabela livros sendo populada em tempo real conforme as buscas acontecem — é a forma mais direta de separar "problema de rede" de "problema de banco".
